# 世界の記録と、話が尽きない仕組み

workflow.md が「**どの順で進めるか**」なら、ここは「**どう貯めるか**」。

## 何のためにあるか

話が続かなくなる理由は、たいてい二つしかない。

1. **前に何を決めたか忘れる。** 設定を全部読み直さないと書けなくなる
2. **次に何が起きるか思いつかなくなる。** 世界が静止していて、
   書き手が毎回ゼロから事件を発明している

どちらも、**世界の状態を時間つきで持っていない**ことから来る。
だから、設定を文章で持つのとは別に、**記録**として持つ。

## 記録は db に持つ

記録は `novel.db`(SQLite)の中にある。**md のファイルは記録ではない。**

- **形は `DEM/db/schema.py` が一か所で決めている。** どのレコードにどの欄が
  あるかはここだけを見る。欄を増やしたければ `schema.py` を直し、
  alembic でマイグレーションを一本切る(`DEM/db/alembic/`)
- **db を直に開かない。** 読むのも書くのも `DEM/claude_interface/` 配下の
  入口を import して呼ぶ。今ある入口の一覧は `IHG/entrypoints.md` にある
- **`worlds/` の md は読む専用の写し。**
  `DEM.claude_interface.sync.export_db.ExportDb().run()` が db から作り直す。
  **md を直しても db には戻らない**(戻す向きの `import_db` もあるが、
  db を本体として扱う前提は変わらない)
- **参照は id で持つ。** 他のレコードを指す欄(`parent_id` `location_id`
  `character_id` …)には名前ではなく id を渡す。実在するかどうかは
  「確定する」側の入口が確かめる
- **欄に書けることを `text` に紛れ込ませない。** `text`(`MarkdownBase` の列)は
  人間が読む文章のほう。種別・所属・時刻のように欄がある情報は欄に入れる。
  逆に、欄を持たないもの(人物の見た目など)は `text` に文章で書く

### レコードの種類

| レコード                                 | 何を持つか                                                     |
| ---------------------------------------- | -------------------------------------------------------------- |
| `location`(場所)                         | 世界線・星・大陸・国・町・村。親を指して木になる                |
| `location_resource`(資源)                | 場所に紐づく資源。`start` の総量から `end` の 0 へ線形に減る    |
| `event`(出来事)                          | 起きたこと。**行動もここに入る**                                |
| `event_character` / `event_object`        | 出来事 ↔ 人物・個体の中間テーブル(多対多)                      |
| `plot`(筋書き)                           | その場所の出来事生成に渡したい筋書き。場所を省けば世界全体に効く |
| `object`(個体)                           | 国・組織・仕組み・群として振る舞うもの                          |
| `object_place` / `character_place`(居場所) | 誰(何)がいつどこに居たか。上書きせず行を足す                   |
| `character`(人物)                        | 一人ひとりの人間。いちばん欄が多い                              |
| `character_drive`(情動)                  | 欲・嘘・必要・恐れ。強度と期間つき                              |
| `term`(語)                               | 呼び名。上位の語にぶら下げられる                                |
| `story`(作品)                            | 企画。どの世界線のどこ・いつに立つか、語り、状態                |
| `episode`(話)                            | **原稿そのもの。** 話数・題・字数・同期フラグ                   |

**種別(kind)のテーブルは無い。** 場所・語が持つ `kind` の文字列がそのまま
種別になる(旧 `kind` 表は廃止した)。**出来事(event)には `kind` 欄自体が
無い。** 断面に出す/出さないだけを `hidden`(真偽値)で持ち、`指標` `関係`
のような分類は `name` の書き方の慣例で表す(下の「出来事は一種類しかない」)。

### 居場所は上書きしない

`character_place` `object_place` は、**場所が変わったら行を足す。**
前の行の `end` を閉じて、新しい行を `start` から始める。
一つの場所にとどまらず何度でも変わる値なので、履歴がそのまま残るようにする。

### 個体と人物の線引き

**「みんな」と言えるなら個体、「この人」としか言えないなら人物。**

- **個体は群の振る舞いを持つ。** 魔族が追われる、商人組合が名簿を握る、
  神殿が登録を絞る。誰か一人の意思ではなく、**まとまりとしての動き**
- **人物は一人ひとりの中身を持つ。** 何を欲しがり、何を信じ違え、何を恐れるか。
  背丈も、一人称も、口調も、人物にしかない

**人物は所属として個体を指す**(`character.belong_id`)。
種族・生まれの性質は個体の側に書き、人物の側へ写さない。
種族そのものを指したくなったら、`belong_id` に種族を表す個体を置く。

**個体も行動の主語になる。** 出来事に掛かれるのは人物だけではない
(`event_object`)。国・組織が何を決め、何を動かしたかは個体の行動として積む
(「出来事の text は記録として書く」)。

### 人物がいちばん細かい理由

本文は一人称・二人称・三人称で人を指す。**その三つが決まっていないと書けない。**

| 欄                                                                                                                                                             | 何のためにあるか                                                                                  |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `first_person` `second_person`                                                                                                                                 | 台詞が誰のものか、読者が名札なしで分かるため(characters.md)                                       |
| `third_person`                                                                                                                                                 | **地の文がこの人物をどう呼ぶか。** 途中で変えない                                                 |
| `tone`(口調)                                                                                                                                                   | 語彙・文の長さ・語尾。**語尾芸に頼らない**                                                        |
| `sincerity` `curiosity` `proactivity` `cooperativeness` `sociability` `emotional_expression` `self_esteem` `self_efficacy` `stress_resilience` `flexibility_of_values` `sensitivity` `imagination` | **性格を 12 軸の数値で持つ。** 同じ状況で何に注目し、何に揺れるかを数で比べられる |
| `world_influence`                                                                                                                                              | この人物(個体)の一手が世界にどれだけ及ぶか                                                        |
| `sex` `height` `build`                                                                                                                                         | 絵にするとき迷わない分だけ。**見た目に当たる欄は無い。`text` に書く**                             |
| `start` `end`                                                                                                                                                  | **生没もこの二つで表す。** 別の欄は無い                                                           |

**能力・特徴も欄ではない。** 表に分けず、`character.text` に文章として書き込む
(旧「技能」システムは廃止した)。出来事の結果として能力が変わったときは
`UpdateCharacter` で `text` を書き直す。

### 情動は欄ではない

欲・嘘・必要・恐れ・感情の揺れは、`character_drive` として積む。
`text` と `level`(強さ)、`start` `end`(いつからいつまで抱えていたか)を持つ。

**情動は、その人物の信念・思考の核になる情報として扱う。** 作成時
(初期状態としての付与)か、その人物にとって大きな出来事があったときにだけ
設定する。日常の細かな出来事のたびに積み増さない。`CommitEvent` の
`character_drives` に乗せるときも、`event_progression_generator` が数日おきに
回す出来事のときも同じで、出来事が信念を揺らすほどのものでなければ
情動は足さない。

嘘を捨てたら行を書き換えるのではなく、**新しい情動を足して、古いものの
`end` を閉じる。** 積み重なりがそのまま人物の変化の記録になる。

### 語と個体は役割が違う

「さいはい」という**組織**は個体、「さいはい」という**語**(正式名称は
再配分機構)は語。**名前は語の側、振る舞いは個体の側。** 両方あってよい。

## 出来事は一種類しかない

**起きたこと・数・間柄・張っているもの。全部「出来事」として積む。**
分ける表は持たない。**`kind`(種別)欄は廃止した**(下の「なぜ `kind` を
廃止したか」)。何を積んでいるかは、`name` の書き方の慣例と `text` の
中身で区別する。

| 何を入れるか                     | 書き方                                       |
| --------------------------------- | -------------------------------------------- |
| 起きたこと(自由)                 | 終わっていないなら `end` を空にする          |
| 数で追えるもの。人口・資源・値段 | `name` を「人口 27400000 人」の形に          |
| 誰と誰が、どういう間柄か         | 下を見る                                     |

間柄を表す出来事は、`text` の書き出しの形まで決まっている。強度(-3 敵対 〜
3 親和。0 は無関心)と、誰と誰の間柄かを最初に書く。

```
name: 命令を送る側と、拒めない側
text: 強度 -2。間柄: さいはい ↔ 采配
      (以下、何がそうさせているか)
```

**関係する双方を、同じ一件に掛ける。** 人物なら `character_ids`、個体なら
`object_ids` に両方の id を入れる(多対多なので、片側だけに寄せる必要はない)。
片方にしか掛けないと、もう片方の断面に出ない。

### なぜ `kind` を廃止したか

出来事の `kind` は元々「自由記述だが `災害` `制度` `政治` `技術` `経済`
`争点` `移動` `発見` `時代` の九つ(+ `指標` `関係`)に収めるのが規約」
という運用だった。だが規約は `DEM/local_ai/`(常駐ループ)の生成プロンプトへ
渡していなかったため、**規約を読めないローカルの小型モデルが、出来事の
たびに長い言い回しの `kind` を作文し続けた**(2026-09、114 件の出来事で
kind がほぼ一意に氾濫しているのを実際に観測)。「一言で」という指示も
守られず、種別が氾濫するほど、それ自体が同じ出来事を名前だけ変えて
繰り返している兆候を隠してしまう。

`kind` が実際にコードから参照されていたのは「断面(`ReadBrief`)から
伏せる」判定だけだったので、そこだけを専用の `hidden`(真偽値)に
切り出し、`指標` `関係` のような分類は `name` の書き方の慣例に落とした。
規約が要らなくなったのではなく、**規約を運用で守らせる場所を、渡せない
プロンプトから、渡さなくても効く欄の形に移した。**

### 出来事の text は記録として書く

`CommitEvent` の `text` の書き方(小説ではなく記録として書く・その場に
あるもの同士の関係から立てる)、直近の出来事を何件まで見るか、人物・個体の
`text` の更新のしかたは、
**`DEM/ai_instructions/event_writing.py` が正本。** Claude が `CommitEvent`
を呼ぶときも、`DEM/local_ai/`(常駐ループ)が出来事を生成するときも、
同じ定数の文面をそのまま基準にする。**ルールの文面を変えたくなったら、
このファイルではなく `event_writing.py` を直す。**

なぜ二つに分けたか、なぜその形にしたかだけここに残す。

- **出来事は小説ではなく、情報整理のための記録**(`EVENT_RECORD_INSTRUCTION`)。
  実際のストーリーは話(`episode`)の側で別に書く。出来事の側で文体やセリフの
  言い回しまで決めてしまうと、**同じ内容を二か所で書くことになる**うえ、
  先に決まった言い回しが本文を縛る。出来事が持つのは、**物事がどう変わったか・
  関わった人物が何を感じたか・誰とどの組織が何をしたか**という、後から引ける
  中身だけにする(発端・行動・感情・変化と影響の四つを順に書く)
- **国・組織のような個体も行為の主体**(`OBJECT_ACTION_INSTRUCTION`)。
  人物一人ひとりの動きだけを積むと、世界が「その場に居た数人の私事」で
  埋まっていく。国・組織・軍・商会が何を決め、何を動かしたかを個体の名前を
  主語にして書かせることで、人物の行動がその決定との関係(従う・背く・
  利用する)として立つ
- **出来事は、その時その場にあるもの同士の相互関係から立てる**
  (`EVENT_RELATION_INSTRUCTION`)。渡した人物・個体・場所・資源のうち
  二つ以上を必ず噛み合わせる。一人(一個体)だけで完結する出来事ばかりだと、
  記録が並んでも世界の関係は何も動かない
- **個体の `text` も人物と同じように積み足す**(`OBJECT_TEXT_UPDATE_INSTRUCTION`)。
  組織が行為の主体である以上、出来事を通して見えたその組織の性質・方針・
  立場も残らないと、次の生成で同じ組織が毎回のっぺらぼうから始まる。
  上限・区切りは人物と同じ(`CHARACTER_NOTE_LIMIT`)
- **常駐ループは対話越しに `IHG/*.md` を読めない。** だから文面は
  Python の定数として持ち、`event_progression_generator.py`(出来事の生成)
  と `character_lifespan.py`(死亡時の出来事)のシステムプロンプトに
  そのまま埋め込む。Claude も同じ文面を直接読みに行く前提にすることで、
  同じ内容を IHG 側にも書き写す**二重メンテを避ける**
- **直近の出来事の参照件数を絞ってある**(`RECENT_EVENT_LIMIT`)。件数を
  増やすほど、過去に使った比喩や語彙(一度使うと繰り返しやすい抽象語)が
  そのまま次の出来事に持ち越され、同じ人物・同じ場所の中で語彙が自己増殖
  していく
- **禁止したい言い回しの具体例をシステムプロンプトに直書きしない**。
  避けたい語をそのまま例示すると、命令の遵守が弱い小型モデル(ローカルで
  使う gemma3n:e2b/e4b など)には**否定命令より例示された語の方が強く残り、
  かえってその語を呼び出しやすくする**(2026-09 に実際に観測: 禁止語の
  例示が入った当時の `EVENT_RECORD_INSTRUCTION`(旧 `EVENT_SCENE_INSTRUCTION`)
  のもとで、例示した語そのものが出来事の text に繰り返し出る「ノイズ」
  「違和感」傾向が起きた)。避けたい傾向は「何をしないか」の具体語ではなく、
  「何を(場所・人物固有の具体を)使うか」という**肯定形**でしか書かない
  (「小説として書かない」「セリフを書かない」は**形式**の指定であって
  避けたい語の例示ではないので、ここには当たらない)
- **人物・個体の `text` に追記できる件数にも上限がある**(`CHARACTER_NOTE_LIMIT`)。
  `RECENT_EVENT_LIMIT` は「出来事一覧」を絞るだけで、人物の `text` は
  上書きせず無限に積み足される設計(次項)なので、そちらは別に絞る必要が
  ある。絞らないと、一度紛れ込んだ語彙がその人物に永久に残り、その人物が
  絡む全ての将来の出来事に繰り返し持ち込まれる
- **人物の `text` は追加形式・パーソナリティだけ**(`CHARACTER_TEXT_UPDATE_INSTRUCTION`)。
  状況の要約を書いて上書きすると、その要約が次の出来事の前提として
  持ち込まれ、語彙の固定化・肥大化を早める。だから場所・立場・状況では
  なく性格・信念・人となりだけを書き、既存の `text` を上書きせず積み足す
  (ただし直近 `CHARACTER_NOTE_LIMIT` 件までに切り詰める。生成時の基礎
  説明は常に残る)
- **場所・人物を新しく生む側(`random_location_generator.py`
  `random_character_generator.py`)の `text` も、具体を最低一つ含めるよう
  求める。**「一言で分かる説明」のような薄い指示のままだと、モデルが
  具体的な手がかりを持てず、場所を問わない抽象的なムード語で埋めがちに
  なる
- **Ollama への呼び出しに `temperature` / `repeat_penalty` を明示している**
  (`ai_client._DEFAULT_OPTIONS`)。既定値のままだと、小型モデルほど
  高確率トークン(=使い回しの効く抽象語)へ収束しやすい
- **出来事には `start`〜`end`(進行中と見なす幅)を持たせ、ローカルAI自身に
  `event_duration_days` で日数を決めさせる**(`EVENT_DURATION_INSTRUCTION`)。
  無いと、同じ人物が3日おきのロール(`EVENT_ROLL_INTERVAL_DAYS`)のたび
  毎回新しい出来事に巻き込まれ、前の出来事がまだ続いているはずの間にも
  次々と話が進んでしまう。`end` を過ぎるまではその人物を次の出来事の対象
  から外す(`event_progression_generator._group_by_place` が
  `world_createion_query.busy_character_ids_select` で除く)

### 同じ出来事を名前だけ変えて繰り返さない

出来事は「積む」ものであって、「同じ結末をなぞる」ものではない。
同じ関係者・同じ場所で、似た内容の出来事が、毎回「合意した」
「確かめ合った」で終わるだけなら、それは進展ではなく足踏みの繰り返しで
ある。積み上がった対立・決定を土台に、次はそれを**具体的に一歩動かす**
(決着する・破られる・第三者が絡む・決定的な行動に出る、など)か、
関わる相手・題材を変える。何も動かないなら、無理に出来事を作らず
見送ってよい(「イベントは作者の意思で起こす」——停滞そのものは問題ではない。
問題は、停滞を「同じ要約の量産」で埋めてしまうこと)。

**この基準も、常駐ループ向けに `DEM/ai_instructions/event_writing.py` の
`EVENT_PROGRESSION_INSTRUCTION` として切り出してある。**
`event_progression_generator.py` はこれをシステムプロンプトに埋め込み、
判断材料として直近の出来事の**名前**を渡す(`kind` 廃止前は種別も渡して
いたが、種別自体が氾濫の温床だったので今は名前だけで足踏みを判定させる)。

**「話し合って合意する/対立したまま膠着する」という決着の付け方**も、
同じ内輪の関係者だけで繰り返すと、`EVENT_PROGRESSION_INSTRUCTION` の
禁止に触れる(2026-09、`worlds/plot/4_.md` で実際に観測: 特定の作品の
当事者だけで閉じてきた対立を、作者が手動でプロットを足して外部から
強制的に動かす必要が生じた。当事者の合意・対立だけでは止められない
外的な圧力・利害を持ち込む必要があること自体は、本来どの場所の自動生成
にも共通する話であって、個々のプロットで毎回手当てするものではない)。

そこで `event_progression_generator.py` は、その場に**今いる**顔ぶれの
ほかに二段の受け皿を持つ。

- **一つ上の圏内の候補**(`_reach_objects`)。`read_cast` の「隣の集落に
  いる者も枠に入れる」(`levels=1`)と同じ考え方で、今はこの場に居なくても
  遠隔で働きかけてくる個体を候補として渡す。IP管理団体・規制当局・競合の
  ような既存の個体が近くにあるなら、まずそこから選ばせる
- **`object_founded`**。それでも噛み合う主体が無いときだけ、ローカル AI
  自身がこの出来事の中で新しい個体を誕生させてよい
  (`random_object_generator.py` の月次生成とは別に、出来事の側からも
  個体を増やせる経路)。プロットの無い場所には生まない基準は
  `random_object_generator.py` と同じ

外部の利害関係者を出来事に巻き込みたいときは、まずこの二段が働くように
**関連する個体・筋書きを先に置く**(`CommitObject` `CommitPlot`)。それでも
まだ自動生成では拾えない展開だけを、個別のプロットの `text` に書く。

### 断面に出さない出来事

出来事の `hidden` が立っているものは、断面(`ReadBrief`)に出ない。
住人が知らないことを本文に書かないための欄で、`CommitEvent` に
`hidden: true` を渡して確定する(既定は `false`)。

- **本文を書くとき**: `full=True` を付けない。伏せられたまま書く
- **裏を設計するとき・繋ぎを確認するとき**: `full=True` を付ける

**伏せる仕組みはこの `hidden` だけ。** 裏設定と伏線を区別したければ
`text` の中に書く(欄では分けない)。語の側にはこの絞り込みが無いので、
本文に出したくない呼び名は、そもそも語として確定しないか、
`text` の中で「まだ誰も使っていない」と分かるように書く。

## 無限に続けるための考え方

### 世界は割り算でできている

`SFファンタジー` の骨格は一本の式である——**暮らし向き ＝ 取れる分 ÷ 人の数**。

この式に触るものは、全部物語になる。分子が減れば事件になり、分母が減れば儀式になり、
**誰が分ける権利を持つか**でそのまま政治になる。地球ではそれが政策になり、
ノウルでは生贄になった。**同じ割り算が、星ごとに違う顔をしているだけ**である。

だから `指標` の出来事は飾りではない。**分子と分母を置く場所**であり、
そこが動いた瞬間、書くべき場面が生まれる。

### イベントは作者の意思で起こす

事件を値の推移から機械的に導かない。**何を起こすかは、作者が決める。**
物語が停滞する話数があってもよい。動きがないことも、そのまま書いてよい。

`指標` と `関係` は、次に何を起こすかを考えるための手がかりであって、
それ自体が話を要求する仕組みではない。分子・分母・間柄がどう動いているかを
読んで、そこに作者が意思で事件を差し込む。

### 過去は消さない。積む

**追記式。** 行を書き換えず、新しい時刻の出来事を足す。
`指標` の値が 3540 年に 27000000、4340 年に 10000000 なら、
**八百年かけて減ってきた**ことが残る。推移そのものが、次に書くときの手がかりになる。

### 世界は、こちらが書かない間も進む

`DEM/local_ai/time_keeper/`(常駐ループ)は、Claude を介さず日を進めながら
出来事・人物・個体(国・組織)・場所・資源を生やし続ける。**話の種を切らさない
ための仕組み**で、断面を取るたびに知らない出来事が増えているのは正常な状態である。

- **個体は、人物が居る場所にだけ生まれる**(`random_object_generator`)。
  その決定に従う・背く相手が居なければ、組織があっても何も動かないため。
  月次のこの経路とは別に、出来事の中でも `object_founded` で個体が
  誕生することがある(「同じ出来事を名前だけ変えて繰り返さない」)

- 方向づけたいときは `CommitPlot` で筋書きを置く。場所を指定すればその場所、
  省けば世界全体の出来事生成に渡る(間延びした展開が続くときはここを足す)
- **その時刻をカバーする筋書きが一件も無くなったら、ループは自分で止まる**
  (`main.loop_time` が日を進めるたびに確かめる)。作者の方向づけが尽きた先
  まで無方向に生成し続けないための安全弁で、`CommitPlot` で `start`〜`end`
  が先の筋書きを足せば、そこから再開できる
- 常駐ループが守る基準は `DEM/ai_instructions/` の定数として渡る。
  IHG の文書はそのまま読めないので、要旨を切り出してある(「形は一か所で
  決まっている」)

## 書く前——断面を取る

その話が立つ**場所と年**を決めて、断面を出す。設定を読み直すより先にこれ。

```python
from DEM.claude_interface.story.read_brief import ReadBrief
ReadBrief(<場所id>, "4360", reach=60).run()
```

出るもの。

| 欄                                      | 何が読めるか                                               |
| --------------------------------------- | ---------------------------------------------------------- |
| `place` / `path`                        | その場所そのものと、世界線からの道筋                       |
| `open_events`                           | まだ終わっていない出来事。**背景に置くべきもの**           |
| `recent_events`                         | `reach` 年ぶん(既定 60 年)の直近の出来事                   |
| `present_characters` / `present_objects` | その時点でそこに居る人物・個体                            |
| `terms`                                 | その場所に届いている語                                     |

**年で見る。** `"4354"` はその年いっぱいを指すので、同じ年の後半に書き足した
出来事も材料に入る。場所は**その場所と、その配下**に効く。

モード 2 の材料(同期の確認・直前の話・断面・顔ぶれ)は
`StartStory(<作品id>)` 一本で出る。個別の入口は、出す範囲を変えたいときに使う。

## 書いたあと——記録に戻す

workflow.md「3 世界観更新モード」を見る。**本文に書いたら、記録にも足す。**

```python
from DEM.claude_interface.randomizer.commit_event import CommitEvent
CommitEvent({
    "name": "登録の値が二倍になる",
    "time": "4361/03/01",
    "location_id": <場所id>,
    "character_ids": [<人物id>, ...],
    "object_ids": [<個体id>, ...],
    "text": "(発端・行動・感情・変化と影響。「出来事の text は記録として書く」)",
}).run()
```

**確定する側の入口を呼ぶまで、db には何も残らない。** `create_random_*` は
辞書を返すだけで db に触れない。

## 数を本文に出さない

principles.md は**ステータス画面・レベル・数値で強さを説明することを禁じている。**
この記録はそれに反しない。**反しないように使う。**

- 記録の数は、naming.md でいう**設定側の名**と同じ扱い。**作者だけが見る**
- 「器 4」と本文に書かない。**書くのは、四人ぶんの井戸を一人で汲み上げてしまう場面**
- 数が動いたことは、**必ず場面として書く**(本文の側で、である。
  出来事の `text` は記録として書く)

**数は、何を書くかを決めるためにある。何を書いたかを説明するためではない。**

## 形は一か所で決まっている

| 何を                             | どこが決めているか                                     |
| -------------------------------- | ------------------------------------------------------ |
| レコードの欄                     | `DEM/db/schema.py`(SQLAlchemy のモデル)                |
| 欄の変更                         | `DEM/db/alembic/` のマイグレーション                   |
| 読み書きの入口                   | `DEM/claude_interface/<領域>/<動詞_対象>.py`           |
| 引き方(Select の組み立て)        | `DEM/data_access_logic/query/`                         |
| 出来事の書き方・進め方           | `DEM/ai_instructions/event_writing.py`(**文面が正本**) |
| 名づけ・なろう系回避の要旨       | `DEM/ai_instructions/naming.py` `principles.py`(**正本は `IHG/naming.md` `IHG/principles.md`**) |

`ai_instructions/` の各ファイルでどちらが正本か、なぜそういう分担に
しているかは `IHG/README.md`「常駐ループへ渡す基準」にまとめてある。

**SQL は組み立てない。** 引く条件は時刻とレコードの id だけで表す。
足りない引き方が出てきたら `DEM/data_access_logic/query/` に関数を足し、
`DEM/claude_interface/` に入口を一つ被せる。
