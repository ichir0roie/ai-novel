# 世界の記録と、話が尽きない仕組み

`core/workflow.md` が「一本どう書くか」なら、ここは「**何本でも書けるようにどう貯めるか**」。

## 何のためにあるか

話が続かなくなる理由は、たいてい二つしかない。

1. **前に何を決めたか忘れる。** 設定ファイルを全部読み直さないと書けなくなる
2. **次に何が起きるか思いつかなくなる。** 世界が静止していて、書き手が毎回ゼロから事件を発明している

どちらも、**世界の状態を時間つきで持っていない**ことから来る。
そこで、設定を文章で持つのとは別に、**台帳**として持つ。

### 入れ物は二種類

**レコードとして管理しやすい形と、文章として書きやすい形を、併存させる。**
どちらか一方に寄せると、必ずもう一方が死ぬ。

| | 何で書くか | 何を入れるか |
| --- | --- | --- |
| **表** | `records/*.md` のマークダウン表。**一行 = 一レコード** | 行が短くて数が多いもの。出来事・行動・数・関係・火種 |
| **記事** | **1 ファイル = 1 レコード。** front matter ＋ 本文 | 文章のつくもの。**人物・物・用語・概念** |

記事は、一つのファイルの中で両方を持つ。

```markdown
---
記録: 用語          ← どの台帳に入るか
id: tm-01
名: 信仰
生: 3800
表: 篤いほど魔力が強くなるもの
裏: 森光の摩耗した形
---

# 信仰

**この星では、信仰が篤いほど魔力が強い。迷信ではない。**
（ここから下は人間が読む文章。長さに制限はない）
```

**front matter がレコード、その下が文章。** 同じファイルにあるので二重管理にならない。
**同じことを二度書かない**——front matter に書いたことを本文で繰り返さない。

| | 持ち方 | 読む相手 |
| --- | --- | --- |
| `worlds/<宇宙>/**/*.md` | 文章。**なぜそうなのか**を書く | 人間。**これが正** |
| `worlds/<宇宙>/records/*.md` | 表。**いつ・どこで・誰が・いくつ** | 機械。文章から起こす |
| 記事（front matter つき） | **両方**。レコードと文章が同じファイルにある | 人間と機械の両方 |
| `worlds/<宇宙>/world.db` | SQLite。**組み上げた結果** | ツール。**git に入れない**。いつでも作り直せる |

### 記事の置き場所

**どこに置いてもよい。** どの台帳に入るかは front matter の `記録:` だけで決まる。
ディレクトリは人間の整理用で、機械は宇宙の中の md を全部見る。

| 記録 | 目安の置き場所 | 何を入れるか |
| --- | --- | --- |
| `人物` | `<星>/characters/` | **行動の主語になれるもの。** 個人・組織・国・集団・仕組み |
| `物` | `<星>/objects/` | **主語にならないもの。** 道具・資源・現象・施設 |
| `用語` | `terms/` | **語の側の記録。** 正式名称と通称、表と裏、いつ使われたか |
| `概念` | `concepts/` | その世界がどう動いているかの考え方 |

人物と用語は**役割が違う**ので、両方あってよい。
「さいはい」という**組織**は人物、「さいはい」という**語**（正式名称は再配分機構）は用語。
用語の側から `実体:` で人物を指しておく。**名前は語の側、振る舞いは人物の側。**

**作品もこの宇宙の中にある**（`worlds/<宇宙>/stories/<作品名>/`）。
台帳・設定・本文が同じディレクトリに揃っているので、**作品が宇宙をまたぐことがない。**

**文章が正で、台帳が従。** 食い違ったら文章を直してから台帳を直す。
台帳にしか存在しない設定を作らない（`CLAUDE.md`「設定の一元管理」と同じ縛り）。

## 無限に続けるための考え方

### 世界は割り算でできている

`worlds/地球系` の骨格は一本の式である——**暮らし向き ＝ 取れる分 ÷ 人の数**。

この式に触るものは、全部物語になる。分子が減れば事件になり、分母が減れば儀式になり、
**誰が分ける権利を持つか**でそのまま政治になる。地球ではそれが政策になり、
入植星では生贄になった。**同じ割り算が、星ごとに違う顔をしているだけ**である。

だから `指標.md` は飾りではない。**分子と分母を置く場所**であり、
そこが動いた瞬間、書くべき場面が生まれる。

### 話は火種から生える

事件を発明しない。**張っているものを探して、それを切る。**

`火種.md` には、対立軸と「値が限界まで行くと何が起きるか」が書いてある。
一本書くというのは、**どれかの火種の値を動かすこと**である。

- 値が上がったなら、次の話が近づいた
- 値が下がったなら、誰かが何かを差し出して抑えた。**その代償を `行動.md` に書く**
- 一本書いても何の値も動かないなら、その話は削れる（`core/workflow.md`「変化するもの」と同じ判定）

**火種は減らない。** 一つ切れば、切った側に新しい火種が立つ。
配る権利を奪った者は、次の話では配る側として憎まれる。そこが尽きない理由である。

### 過去は消さない。積む

台帳は**追記式**。行を書き換えず、新しい年の行を足す。
`火種.md` で ts-0011 が 3540 年に 3、4340 年に 4 なら、**八百年かけて張ってきた**ことが残る。
推移そのものが、次に書くときの手がかりになる。

## 書く前——断面を取る

その話が立つ**星・年・場所**を決めて、断面を出す。設定ファイルを読み直すより先にこれ。

```
python3 tools/chronicle.py brief --world 地球系 --star 入植星 --year 4360 --place mushvan-land
```

出るもの。

| 節 | 何が読めるか |
| --- | --- |
| 1 いまの数値 | 分子と分母。前回からの動き |
| 2 続いている出来事 | この時点でまだ終わっていないもの。**背景に置くべきもの** |
| 3 直近の出来事 | 登場人物が覚えている範囲の過去 |
| 3.5 この射程での行動 | 誰が何をして、**何を失ったか**。代償が残っているうちは、まだ効いている |
| 4 その場にいる者 | 年齢つき。死んだ者と生まれる前の者は出ない |
| 5 関係 | 誰が誰をどう見ているか |
| 6 張っている火種 | **次の一手の候補** |
| 6.5 この年に使える語 | **その年に生きている語だけ。** 死語と、まだ無い語は出ない |
| 7 他の星から届いている信号 | 光の遅れを引いた範囲だけ |
| 8 この星からは見えないこと | 件数だけ。`--full` で中身が出る |

`--place` を付けると、**その場所・その内側・その外側**に絞られる。
外側から来たものには「（広域）」が付く。それが**周辺環境**である。

### 視点を守る

`公開` 列は「**誰から見えるか**」を持っている。

| 値 | 意味 |
| --- | --- |
| `公然` | 全員が知っている |
| `秘匿` | 誰も知らない。**作者だけ** |
| 星名（`地球` / `入植星`） | その星の人間だけが知っている |

既定の `brief` は、その星から見えない行を**伏せる**。これは不便のためではない。
`worlds/地球系/入植星/解釈表.md`「表の物語の本文には、裏の語を一つも出さない」を、
**台帳の側から守るため**である。

- **本文を書くとき**: `--full` を付けない。伏せられたまま書く
- **裏を設計するとき・繋ぎを確認するとき**: `--full` を付ける

八節に件数が出るのは意図的で、「**この時点には、まだ書けないことが 5 件ある**」と
分かっているほうが、住人の無知を正しく書ける。

## 書いたあと——台帳に戻す

`core/workflow.md`「6. 設定の書き戻し」の続き。**文章に書き戻したら、台帳にも足す。**

```
python3 tools/chronicle.py add --world 地球系 --table event \
  --set 年=4361-03 --set 星=入植星 --set 場所=mushvan-land \
  --set 種別=経済 --set 規模=2 --set 公開=公然 \
  --set 出来事="登録の値が二倍になった" --set 関与=kumiai --set 出典="stories/<作品名>/episodes/001.md"
```

`id` は自動で振られ、書いたあと DB が組み直される。

一話書いたら、最低でも**これだけは足す**。

| 台帳 | 足すもの |
| --- | --- |
| `出来事.md` | その話で起きたこと |
| `行動.md` | 主要人物がやったこと。**動機と代償と結果をそろえて** |
| `火種.md` | 動いた火種の新しい行。動いていないなら、その話は弱い |
| `人物.md` | 出した人物。**本文に名前を出した時点で登録する** |
| `指標.md` | 数が動いたなら |

最後に検査する。**エラーが残ったまま次の話へ行かない。**

```
python3 tools/chronicle.py check --world 地球系
```

## 数を本文に出さない

`core/principles.md` は**ステータス画面・レベル・数値で強さを説明することを禁じている。**
この台帳はそれに反しない。**反しないように使う。**

- 台帳の数は、`core/naming.md` でいう**設定側の名**と同じ扱い。**作者だけが見る**
- 「器 4」と本文に書かない。**書くのは、四人ぶんの井戸を一人で汲み上げてしまう場面**
- 火種の値は、緊張の量を作者が測るための目盛りであって、作中の誰も知らない
- 数が動いたことは、**必ず場面として書く**（`CLAUDE.md`「要約で済ませない」）

**数は、何を書くかを決めるためにある。何を書いたかを説明するためではない。**

## 数の決め方

台帳に入れる数のうち、設定ファイルから読めないものは**乱数で振る**
（`core/principles.md`「ランダム要素の使い方」）。

```
python3 tools/roll.py --num 200 3000 --step 10 --label 入植星総人口万人
```

- 引いた目とシードは `worlds/<宇宙>/rolls.md` に残す
- 前後関係に矛盾するなら調整してよい。**調整前の値と理由もログに残す**
- `指標.md` の `出典` 列に `rolls.md（乱数）` と書いて、**どれが振った数かを分かるようにする**

**例外は火種の値。** これは乱数ではなく、設定から読めるかどうかで決める。
設定を読んで張っていないものは、まだ火種ではない。

## 台帳の形

**形は `tools/schema.py` が一か所で決めている**（SQLAlchemy のモデル）。
DB の列も、マークダウンの列見出しも、検査の内容も、そこから出ている。
列を増やしたければ `schema.py` を直す。**マークダウン側に勝手な列を足さない。**

```
python3 tools/chronicle.py schema                  # いまの形を表示する
python3 tools/chronicle.py template --kind 人物     # 記事の雛形を出す
```

見出しがスキーマと食い違う表は、**取り込まれずエラーになる**。
黙って行が消えるより、止まったほうがいいという判断。

台帳は `worlds/<宇宙>/records/` に置く。全部マークダウンの表で、
**列の見出しが機械の読む鍵**になる。

| ファイル | 何を貯めるか | 時間 |
| --- | --- | --- |
| `場所.md` | 地理。親をたどって内側・外側を決める | なし |
| `出来事.md` | 起きたこと | 年／終年 |
| `行動.md` | **主語のある**出来事。動機・代償・結果つき | 年 |
| `指標.md` | 数で追えるもの。人口・資源・値段 | 年 |
| `関係.md` | 誰と誰が、どういう間柄か。強度 -3〜3 | 年／終年 |
| `火種.md` | 張っているもの。値 0〜5 と、限界で起きること | 年 |

人物・物・用語・概念は表ではなく**記事**（1 ファイル 1 レコード）。上の「記事の置き場所」を見る。

書き方の細かい規約は各ファイルの冒頭にある。共通するのは三つ。

- **年は西暦。** `4360` / `4360-07` / `4360-07-12` のどれでもよい。混ぜてよい
- **出典のない行を足さない。** どの設定ファイルから来たかを必ず書く
- **セル内の `|` は `\|` と書く。** 改行は使えない（`<br>` で代用）

新しい宇宙を作るときは `records/` ごと作る。`config.json` に星と光の遅れを書けば、
七つの台帳は空のままでも `brief` が動く。

## ツール

```
pip install -r requirements.txt     # SQLAlchemy が要る
```

| ファイル | 役割 |
| --- | --- |
| `tools/schema.py` | **台帳の形。** SQLAlchemy のモデル。DB の列とマークダウンの見出しを決める |
| `tools/ledger.py` | マークダウンの読み書きと、**DB への取り込み** |
| `tools/chronicle.py` | 入口。下のコマンドを持つ |

| | |
| --- | --- |
| `init --world <宇宙名>` | **新しい宇宙**に台帳の雛形と `stories/` を作る |
| `template --kind 人物` | **記事の雛形**を出す（人物／物／用語／概念） |
| `entry <id か名>` | 記事を一件読む |
| `list --kind 用語 --year 4360` | 記事の一覧。その年に在ったものだけに絞れる |
| `index` | 記事の索引を `glossary.md` に書き出す |
| `build` | 台帳から DB を組み上げる |
| `check` | 矛盾を探す。**エラーがあれば終了コード 1** |
| `brief` | 断面を出す |
| `series --metric 人口` | 指標の推移を出す |
| `add --table event --set 年=...` | 台帳に一行足して、組み直す |
| `sql "SELECT ..."` | 直接問い合わせる |
| `worlds` | 宇宙の一覧 |
| `schema` | 台帳の形を表示する |

`--world` を省くと、記録のある宇宙が一つだけならそれを使う。

`sql` は、断面では出ない問いに使う。たとえば一人あたりの取り分。

```
python3 tools/chronicle.py sql --world 地球系 \
  "SELECT a.t0, a.place, a.value / b.value FROM metric a JOIN metric b
   ON a.t0 = b.t0 AND a.place = b.place WHERE a.name='配分量' AND b.name='人口'"
```

`world.db` は git に入れない。**台帳から何度でも組み直せる**ので、
差分が読めないバイナリを履歴に残す意味がない。
新しい環境では最初に `build` を一度走らせる（`brief` は無ければ勝手に組む）。

## 一本書くときの流れ

```
pip install -r requirements.txt                          # 初回だけ
python3 tools/chronicle.py build  --world <宇宙>          # 台帳 → world.db
python3 tools/chronicle.py brief  --world <宇宙> --star <星> --year <年> --place <場所>
                                                         # ↑ これを読んでから書く
（worlds/<宇宙>/stories/<作品名>/episodes/NNN.md に本文を書く）
（生まれた設定を worlds/<宇宙>/ の文章側へ書き戻す）
python3 tools/chronicle.py add    --world <宇宙> --table event --set ...
python3 tools/chronicle.py add    --world <宇宙> --table tension --set ...
python3 tools/chronicle.py index  --world <宇宙>          # 語を足したら索引を作り直す
python3 tools/chronicle.py check  --world <宇宙>          # エラー 0 で終わる
```

**人物・物・用語・概念は `add` では足せない。** 文章がつくので、ファイルとして書く。

```
python3 tools/chronicle.py template --kind 人物 > worlds/<宇宙>/<星>/characters/<名>.md
（front matter を埋め、その下に文章を書く）
python3 tools/chronicle.py build --world <宇宙>
```

**この順番を崩さない。** 断面を読まずに書くと前と矛盾し、
台帳に戻さずに次へ行くと、次の断面が嘘になる。
